<Section id="problem">

A sports club renews memberships every year. The steps are always the same: check that the member may renew, work out the fee, charge it, issue the card and send a welcome note. Juniors and seniors differ in who may renew and what they pay, so the first version has one class for each, and the second class starts as a copy of the first:

<Grid cols="1fr 1fr" narrowCols="1fr">
<AnnotatedCode
  wide={false}
  caption="JuniorRenewal"
  code={`
public class JuniorRenewal
{
    public string Renew(string m, int age)
    {
        if (age >= 18) return "too old";
        var fee = age < 12 ? 20 : 30;
        var r = $"{m} charged {fee}";
        return r + ", card issued";
    }
}
`}
  marks={[
    { line: 7, tone: 'bad', badge: '1' },
    { line: 8, tone: 'bad', badge: '3' },
  ]}
/>
<AnnotatedCode
  wide={false}
  caption="SeniorRenewal"
  code={`
public class SeniorRenewal
{
    public string Renew(string m, int age)
    {
        if (age < 60) return "too young";
        var card = "card issued";
        var r = $"{m} paid 40";
        return r + ", " + card;
    }
}
`}
  marks={[
    { line: 6, tone: 'bad', badge: '2' },
    { line: 7, tone: 'bad', badge: '1' },
    { line: 8, tone: 'bad', badge: '3' },
  ]}
/>
</Grid>

It works, but <Key>the order of the steps is written out in every class</Key>, and the copies have already drifted apart:

<BadgeList tone="bad" count={3}>

1. A fix lands in one copy only. The receipt says `charged` in `JuniorRenewal` and `paid` in `SeniorRenewal`: someone reworded one and missed the other.
2. The order itself has drifted. `SeniorRenewal` issues the card before it charges, so a member could get a card without paying.
3. The two `return` lines build the receipt in different ways. A welcome note means editing both of them, and each new kind of member means one more.
4. A third kind of member, such as a family, is a third copy of all of it.

</BadgeList>

<KeyIdea>

Write the steps and their order once, in a base class, and let each subclass fill in only the steps that differ.

</KeyIdea>

</Section>

<Section id="structure">

Template Method has one base class and as many subclasses as there are kinds of renewal. The base class owns the method that runs the steps, and the subclasses answer the steps that are left open.

The base class is <Role kind="primary">MembershipRenewal</Role>. Its method `Renew` is the **template method**: it calls the steps in a fixed order. In C# it is an ordinary method that is not `virtual`, so a subclass cannot override it.

The subclasses are <Role kind="concrete">JuniorRenewal</Role> and <Role kind="concrete">SeniorRenewal</Role>. Each overrides only the two steps that differ: `IsEligible` and `WorkOutFee`.

The five steps are not all the same kind, and the next figure shows which is which.

<Figure

>

A **required step** is `protected abstract`, so every subclass must answer it. A **fixed step** is `private` and lives in the base class. A **hook** is `protected virtual` with a default body, here an empty string: a subclass may override it, and does not have to.

`Renew` checks eligibility, works out the fee, charges it, issues the card and calls the welcome-note hook, always in that order. If the member is not eligible, it stops after the first step. <Key>The order lives in one place</Key>, so a fix to `Charge` reaches every kind of member.

<Role kind="concrete">JuniorRenewal</Role> says who may renew and what a renewal costs, and nothing else. It does not call `Charge` or `IssueCard`, and it does not decide when it is asked. <Key>The base class calls the subclass</Key>, not the other way round. The hook is the same kind of call: `WelcomeNote` is asked every time, and the default answers with nothing.

</Point>

The base class sets the order, the subclasses fill in the blanks, and that is why a fix to the order is made once.

<Section id="example">

The example renews Mia (14) and Ola (19) as juniors and Tomas (67) as a senior. Run it and you should see three lines: `Mia charged 30 EUR, card issued`, `Tomas charged 40 EUR, card issued` and `Ola: not eligible at 19`. The third shows that the fixed order can stop early: <Role kind="concrete">JuniorRenewal</Role> answers `IsEligible` with false, so `Renew` returns before it works out a fee or charges anyone.

Then change it. Add a family renewal that sends a welcome note. There are two edits.

1. After the line that prints Ola's renewal, add `Console.WriteLine(new FamilyRenewal().Renew("Dana", 40));`. It goes with the other statements at the top, above the class declarations.
2. At the end of the file, after `SeniorRenewal`, add a class `FamilyRenewal` that extends <Role kind="primary">MembershipRenewal</Role>. Make `IsEligible` return `age >= 18` and `WorkOutFee` return `60`, both as `protected override`. Also add `protected override string WelcomeNote(string member) => $", welcome note sent to {member}";`, which overrides the hook.

You should now see a fourth line, `Dana charged 60 EUR, card issued, welcome note sent to Dana`. The other three lines stay as they were. <Key>The hook is optional</Key>: the other two subclasses leave it alone, and <Role kind="primary">MembershipRenewal</Role> did not change.

<Section id="when-to-use">

Use Template Method when:

<Checklist>
  <Verdict ok><span>several classes <Key>follow the same steps in the same order</Key>, and only some of the steps differ;</span></Verdict>
  <Verdict ok><span>you want the order <Key>in one place</Key>, so that a fix to a shared step reaches every class;</span></Verdict>
  <Verdict ok><span>some steps are <Key>optional</Key>, and a hook with a default body lets a subclass add them without forcing the others to.</span></Verdict>
  <Verdict ok={false}><span>**Skip it** when there is only one kind, or when the kinds share almost nothing. A plain method is simpler than a base class with nothing to fix.</span></Verdict>
</Checklist>

### Pitfalls

<Pitfall title="A template that subclasses can override">

The point of the pattern is a fixed order. If `Renew` is `virtual`, a subclass can replace it, and the guarantee is gone: the override below issues a card without checking or charging anyone. In C# a method can be overridden only when it is `virtual`, `abstract` or itself an `override`, so write `Renew` as a plain method.

<CodePair
  bad={"// MembershipRenewal\npublic virtual string Renew(string member, int age)\n{ ... }\n\n// JuniorRenewal\npublic override string Renew(string member, int age)\n    => $\"{member}: card issued\";"}
  good={"// MembershipRenewal\npublic string Renew(string member, int age)\n{ ... }\n\n// JuniorRenewal: only the steps\nprotected override bool IsEligible(int age)\n    => age < 18;"}
  badLabel="a subclass can skip the steps"
  goodLabel="not virtual, steps only"
/>

</Pitfall>

<Pitfall title="Too many steps left open">

Each abstract step is something every subclass must write. If every subclass would write the same `Charge`, you have copied the same code again, which is the problem the pattern solves. Make a step abstract only when the subclasses really differ, keep a shared step in the base class, and make an optional one a hook.

<CodePair
  bad={"protected abstract bool IsEligible(int age);\nprotected abstract int WorkOutFee(int age);\nprotected abstract string Charge(string member, int fee);\nprotected abstract string IssueCard();"}
  good={"protected abstract bool IsEligible(int age);\nprotected abstract int WorkOutFee(int age);\n\nprivate string Charge(string member, int fee)\n    => $\"{member} charged {fee} EUR\";"}
  badLabel="every subclass writes Charge again"
  goodLabel="only what differs is open"
/>

</Pitfall>
