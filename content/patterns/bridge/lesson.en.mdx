<Section id="problem">

A podcast app has two kinds of player controls: a basic one with play and pause, and a podcast one that adds skip 30 seconds. Each plays through an output, the phone speaker or headphones. The first version writes <Key>one class for every pair</Key>:

<AnnotatedCode
  caption="The first version: a class per control style and output"
  code={`
public class PodcastSpeakerPlayer
{
    public void Play(string title) =>
        Console.WriteLine($"Speaker: playing {title}");
    public void Skip30() =>
        Console.WriteLine("Speaker: jump 30 s");
}

public class PodcastHeadphonePlayer
{
    public void Play(string title) =>
        Console.WriteLine($"Headphones: playing {title}");
    public void Skip30() =>
        Console.WriteLine("Headphones: jump 30 s");
}

// ...and BasicSpeakerPlayer and BasicHeadphonePlayer: four classes in all.
`}
  marks={[
    { line: 1, tone: 'bad', badge: '1' },
    { line: 4, tone: 'bad', badge: '2' },
    { line: 6, tone: 'bad' },
    { line: 9, tone: 'bad' },
    { line: 11, tone: 'bad' },
    { line: 12, tone: 'bad' },
    { line: 13, tone: 'bad' },
    { line: 14, tone: 'bad' },
    { line: 17, tone: 'bad', badge: '3' },
  ]}
/>

It plays, and the classes <Key>multiply</Key> as soon as either side grows:

<BadgeList tone="bad" count={3}>

1. Every pair of control style and output is its own class. Two styles on two outputs are four classes, and a third of each makes nine.
2. The output's code is copied into every class. The line that prints "Speaker: playing" is written in every speaker class, and a change to the speaker has to be made in each copy.
3. A new output means one new class for each control style, and a new control style means one new class for each output. One forgotten pair is a player that cannot play on that output.
4. Adding a control style and adding an output are two separate jobs, but the code treats them as one: copying classes.

</BadgeList>

<KeyIdea>

There are two things that change, the controls and the output. <Key>Keep them apart</Key> and join them with one reference, so each can grow on its own.

</KeyIdea>

</Section>

<Section id="analogy">

Think of the wall switches and lamps in a house. A switch can be a toggle or a dimmer. A lamp can be a desk lamp or a ceiling light. You do not buy a "dimmer desk lamp" and a "toggle ceiling light" as single products. Every switch works with every lamp, because they <Key>meet at the wiring</Key>.

Fit a new kind of lamp and every switch controls it. Fit a new kind of switch and it controls every lamp. Neither side changes when the other grows.

Bridge has the same shape: the switch is the <Role kind="concrete">player</Role> with its controls, the lamp is the <Role kind="concrete">output</Role>, and the wiring is the <Role kind="contract">IAudioOutput</Role> interface they meet at.

A <Role kind="concrete">player</Role> and an <Role kind="concrete">output</Role> are chosen on their own and <Key>joined at one interface</Key>. A new one of either costs one class, not one per pair.

The control side is the abstract class <Role kind="contract">Player</Role>, called the abstraction. It holds an output and does its work by calling it. <Role kind="concrete">BasicPlayer</Role> and <Role kind="concrete">PodcastPlayer</Role> are the refined abstractions: they add controls and never output code.

The output side is the interface <Role kind="contract">IAudioOutput</Role>, called the implementor. It offers small steps, and <Role kind="concrete">Speaker</Role> and <Role kind="concrete">Headphones</Role> carry them out. It never mentions a player.

<Section id="example">

The example is the program from the scene. Run it and you should see eight lines: for each output, the basic player plays, then the podcast player plays, skips 30 seconds and speeds up. Every line starts with `Speaker` or `Headphones`.

Then change it. Add a `CarStereo` output: one class that implements <Role kind="contract">IAudioOutput</Role>, and add it to the array in the loop. Both players should work on it. You should not need to change <Role kind="contract">Player</Role>, <Role kind="concrete">BasicPlayer</Role> or <Role kind="concrete">PodcastPlayer</Role>, and you write one class, not two.

Notice that the player classes never name an output class, and that the output classes never name a player.

<Section id="when-to-use">

Use Bridge when:

<Checklist>
  <Verdict ok><span>a class would otherwise grow in <Key>two directions</Key>, such as control style and output, and you do not want a class for every pair;</span></Verdict>
  <Verdict ok><span>you want to <Key>add either side on its own</Key>, or choose the output when the program runs;</span></Verdict>
  <Verdict ok><span>several control styles should <Key>share one output</Key>, so its code is written once.</span></Verdict>
  <Verdict ok={false}><span>**Skip it** when only one side varies. A plain interface with its implementations is enough, and a second hierarchy adds a layer nobody needs.</span></Verdict>
</Checklist>

### Bridge or Adapter

Both put a class between two sides. They differ in when the split is made.

### Bridge or Strategy

Both hold another object and hand it work. In a Strategy that object is one algorithm, and the class around it stays one class. In a Bridge the class around it has hierarchies of its own.

### Pitfalls

<Pitfall title="A player that checks the output's type">

If a control asks which output it has and branches, the player depends on the output classes again, and the bridge is only decoration. A new output then means editing the player. Call the interface and let each output answer for itself.

<CodePair
  bad={"public void Skip30()\n{\n  if (Output is Headphones)\n    Console.WriteLine(\"Headphones: jump 30 s\");\n  else\n    Console.WriteLine(\"Speaker: jump 30 s\");\n}"}
  good={"public void Skip30() => Output.Seek(30);"}
  badLabel="the player checks the type"
  goodLabel="the output answers"
/>

</Pitfall>

<Pitfall title="An output shaped like the controls">

If the output interface has a method for every control, each new control has to be added to every output, and the two sides are tied together again. Keep the output to small steps, and build the controls from them in the player.

<CodePair
  bad={"public interface IAudioOutput\n{\n  void Start(string title);\n  void Skip30();   // a control\n  void Faster();   // a control\n}\n// A new control is a new method on every output."}
  good={"public class PodcastPlayer(IAudioOutput output) : Player(output)\n{\n  public void Skip30() => Output.Seek(30);\n  public void Faster() => Output.SetSpeed(1.5);\n}\n// A new control is one new method, here."}
  badLabel="controls in the output"
  goodLabel="steps in the output"
/>

</Pitfall>
