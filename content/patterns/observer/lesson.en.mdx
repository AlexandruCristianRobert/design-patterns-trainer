<Section id="problem">

A weather station measures the temperature. Three displays need every new reading: a phone app, a TV widget and a web dashboard. The first version usually looks like this:

<AnnotatedCode
  caption="The first version: the station knows every display by name"
  code={`
public class WeatherStation
{
    private readonly PhoneDisplay _phone = new();
    private readonly TvDisplay _tv = new();
    private readonly WebDashboard _web = new();

    public void SetTemperature(int temperature)
    {
        _phone.Show(temperature);
        _tv.Show(temperature);
        _web.Render(temperature);
    }
}
`}
  marks={[
    { line: 3, tone: 'bad', badge: '2' },
    { line: 4, tone: 'bad', badge: '3' },
    { line: 5, tone: 'bad' },
    { line: 9, tone: 'bad', badge: '1' },
    { line: 10, tone: 'bad' },
    { line: 11, tone: 'bad', badge: '4' },
  ]}
/>

It works, but the <Key>station now knows every display by name</Key>, and that hurts in several ways:

<BadgeList tone="bad" count={4}>

1. Adding a smartwatch display means editing <Role kind="primary">WeatherStation</Role>, a class that has nothing to do with smartwatches.
2. The set of receivers is fixed at compile time. A user cannot turn the TV widget off while the program runs.
3. You cannot test the station without creating all three displays.
4. Each display has its own method name, so the station also has to know how each one wants to be called.

</BadgeList>

<KeyIdea>

Measuring the temperature is the station's job. Keeping track of who cares about it is a second job, and it is the one that keeps changing.

</KeyIdea>

</Section>

<Section id="analogy">

Think of a newsletter. You subscribe by giving the publisher your email address. When a new issue is out, the publisher sends it to every address on the list. It does not know whether you read it on a phone or print it out, and it does not need to.

You can unsubscribe at any time, and the next issue simply does not reach you. Nobody had to change how the newsletter is written.

The only thing that connects publisher and readers is the list and the agreed format of an issue. Observer has the same shape: the subject keeps a list of subscribers that all share one interface, and sends each of them the same notification when something changes.

Observer has two roles.

The **subject**, here <Role kind="primary">WeatherStation</Role>, owns the state and a list of observers. It offers `Subscribe` and `Unsubscribe`, and whenever its state changes it calls every observer on the list.

The **observer** is an interface with a single method, <Role kind="contract">Update</Role>. Concrete observers such as <Role kind="concrete">PhoneDisplay</Role> and <Role kind="concrete">TvDisplay</Role> implement it.

Look at where the arrows point. The subject <Key>depends only on the interface</Key>, never on a concrete display. A new display is a new class that implements <Role kind="contract">IObserver</Role>; the station does not change. Hover or focus a box to see its code in the example.

Here the station passes the new value into <Role kind="contract">Update</Role>. This is the *push* model. In the *pull* model, <Role kind="contract">Update</Role> takes no data and each observer reads what it needs from the subject. Push is simpler when the payload is small. Pull suits observers that need different parts of a large state.

<Section id="example">

The example is the program from the scene. Run it and you should see three lines: the phone and the TV report 23°C, then only the phone reports 25°C.

Then change it. Add a `WatchDisplay` class that implements `IObserver` and subscribe it in the top-level code. You should not need to touch `WeatherStation` at all. That is the point of the pattern.

Note the `ToList()` in `SetTemperature`. The station loops over a copy of its list, so an observer that unsubscribes from inside `Update` does not break the loop.

<LessonExample />

In everyday C#, `event` is Observer built into the language: `public event Action<int>? TemperatureChanged;`, with `+=` to subscribe and `-=` to unsubscribe. The interface version shows the moving parts explicitly; in production code an event is often the more idiomatic choice. .NET also ships `IObservable<T>` and `IObserver<T>` for push-based streams.

</Section>

<Section id="when-to-use">

Use Observer when:

<Checklist>
  <Verdict ok><span>a change in one object must reach others, and <Key>the set of receivers is open</Key> or changes at runtime;</span></Verdict>
  <Verdict ok><span>the sender should not depend on the receivers' concrete types, for example a domain object that must not know about the UI.</span></Verdict>
  <Verdict ok={false}><span>**Skip it** when there is exactly one receiver and it never changes. A direct method call is easier to read and easier to debug.</span></Verdict>
</Checklist>

### Pitfalls

<Pitfall title="Forgotten unsubscribe">

The subject's list holds a strong reference to every observer. A short-lived observer that subscribes to a long-lived subject and never unsubscribes stays in memory and keeps receiving updates. This is the classic event-handler leak in .NET. Pair every `Subscribe` with an `Unsubscribe`; returning an `IDisposable` from `Subscribe` makes that hard to forget.

<CodePair
  bad="station.Subscribe(view);"
  good="using var sub = station.Subscribe(view);"
  badLabel="never let go"
  goodLabel="disposed with the scope"
/>

</Pitfall>

<Pitfall title="Notification order">

Observers are usually called in the order they subscribed, but nothing in the pattern promises it. If one observer must run before another, that dependency belongs in the code, not in the order of `Subscribe` calls.

<CodePair
  bad={"station.Subscribe(cache);\nstation.Subscribe(view); // view needs cache first"}
  good="view.Update(t) { cache.Refresh(t); Show(t); }"
  badLabel="hidden dependency"
  goodLabel="explicit call"
/>

</Pitfall>

<Pitfall title="Re-entrancy while notifying">

An observer may unsubscribe, or change the subject's state, from inside <Role kind="contract">Update</Role>. Removing an item from a `List<T>` during a `foreach` over it throws `InvalidOperationException`, which is why the example loops over a copy. A state change from inside <Role kind="contract">Update</Role> starts a nested round of notifications; make sure it cannot loop forever.

<CodePair
  bad="foreach (var o in _observers)"
  good="foreach (var o in _observers.ToList())"
  badLabel="breaks if one leaves"
  goodLabel="loops over a copy"
/>

</Pitfall>

<Pitfall title="Observers that throw">

If one observer throws, the loop stops and the remaining observers miss the update. Choose a policy on purpose: let the exception propagate, or catch it per observer, log it and continue.

<CodePair
  bad="o.Update(t);"
  good="try { o.Update(t); } catch (Exception e) { Log(e); }"
  badLabel="one failure stops all"
  goodLabel="the rest still get it"
/>

</Pitfall>
