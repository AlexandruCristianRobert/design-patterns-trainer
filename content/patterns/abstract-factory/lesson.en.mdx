<Section id="problem">

A café sells breakfast sets. Each set is a drink and a main that belong together: the continental set is coffee with a croissant, the English set is tea with a fry-up. The first version usually picks each part <Key>on its own</Key>, from the name of the set:

<AnnotatedCode
  caption="The first version: two choices, one set name"
  code={`
public class BreakfastCounter(string set)
{
    public string Serve()
    {
        IDrink drink = set switch
        {
            "continental" => new Coffee(),
            "english" => new Tea(),
            _ => throw new ArgumentException($"Unknown set: {set}"),
        };
        IMain main = set switch
        {
            "continental" => new Croissant(),
            "english" => new FryUp(),
            _ => throw new ArgumentException($"Unknown set: {set}"),
        };
        return $"{drink.Name} with {main.Name}";
    }
}
`}
  marks={[
    { line: 5, tone: 'bad', badge: '1' },
    { line: 6, tone: 'bad' },
    { line: 7, tone: 'bad' },
    { line: 8, tone: 'bad' },
    { line: 9, tone: 'bad', badge: '3' },
    { line: 11, tone: 'bad', badge: '2' },
    { line: 12, tone: 'bad' },
    { line: 13, tone: 'bad' },
    { line: 14, tone: 'bad' },
    { line: 15, tone: 'bad' },
  ]}
/>

It works, but the drink and the main are two separate decisions that only <Key>happen to agree</Key>:

<BadgeList tone="bad" count={3}>

1. Nothing ties the two `switch` blocks together. Change one and forget the other, and a continental order gets a fry-up with its coffee.
2. A new set, say brunch, means editing both `switch` blocks, and both have to stay in step.
3. A typo in the set name compiles fine and only fails when that order arrives at the counter.
4. The same pair of `switch` blocks tends to spread. The tray, the price and the kitchen ticket each pick by set too, and every copy has to be kept in step.

</BadgeList>

<KeyIdea>

The drink and the main are <Key>one family</Key>, so they should come from one choice, made once, not from two choices that must be kept equal.

</KeyIdea>

</Section>

<Section id="analogy">

Think of a furniture showroom with collections. You pick a collection, Scandinavian or Victorian, and every piece you get from it, the chair, the table and the lamp, matches. You never have to check that the lamp suits the chair, because both came from the same collection.

The choice is made once, at the start. After that you only ask for a chair, a table or a lamp, and the collection decides what you receive.

Abstract Factory has the same shape: a <Role kind="contract">factory interface</Role> lists the pieces, and each <Role kind="concrete">concrete factory</Role> is one collection that makes all of them in its own style. The code that uses the pieces picks a <Role kind="concrete">collection</Role> once and asks it for everything.

The **abstract factory** is the interface <Role kind="contract">IBreakfastKitchen</Role>. It declares one creation method for each kind of product, <Role kind="contract">MakeDrink</Role> and <Role kind="contract">MakeMain</Role>. Each **concrete factory**, <Role kind="concrete">ContinentalKitchen</Role> and <Role kind="concrete">EnglishKitchen</Role>, implements all of them and makes every product in its own family.

The products have interfaces too: <Role kind="contract">IDrink</Role> and <Role kind="contract">IMain</Role>. <Role kind="concrete">Coffee</Role> and <Role kind="concrete">Croissant</Role> are the continental products, <Role kind="concrete">Tea</Role> and <Role kind="concrete">FryUp</Role> the English ones. The dashed «creates» arrows show which kitchen calls `new` on which class.

The client, <Role kind="primary">BreakfastCounter</Role>, points only at interfaces. It holds one <Role kind="contract">IBreakfastKitchen</Role>, so a new family is a new kitchen and new product classes, and the counter does not change. Hover or focus a box to see its code in the example.

<Section id="example">

The example is the program from the scene. Run it and you should see two lines: `Continental: coffee with croissant` and `English: tea with fry-up`, both from the same `Serve` method.

Then change it. Add a third set: write an `OrangeJuice` that implements `IDrink` and a `Pancakes` that implements `IMain`, then a `BrunchKitchen` that makes them, and serve a brunch from the top-level code. You should not need to touch `BreakfastCounter`, `ContinentalKitchen` or `EnglishKitchen`. That is the point of the pattern.

Notice that the two products are made by the same kitchen. A brunch kitchen cannot hand out a croissant by accident, because it is the only place that decides what a brunch contains.

<Section id="when-to-use">

Use Abstract Factory when:

<Checklist>
  <Verdict ok><span>a program works with <Key>families of related products that must be used together</Key>, such as a drink and a main from the same set;</span></Verdict>
  <Verdict ok><span>the client should not know which concrete classes it gets, and the family is decided in one place, such as a setting or the start of the program;</span></Verdict>
  <Verdict ok><span>you want to add a new family, a new set, without editing the code that uses the products.</span></Verdict>
  <Verdict ok={false}><span>**Skip it** when there is only one kind of product, or the products do not have to match. A single creation method, or a plain `new`, is simpler.</span></Verdict>
</Checklist>

### Factory Method or Abstract Factory

Both hide `new` behind a method, and they are easy to confuse. The difference is how much one creator makes, and how it is reached.

<Figure
  caption="One overridable method vs one object"
  description="Two cards. Factory Method: a class declares one overridable method, MakeDrink, and its subclasses, CoffeeStation and TeaStation, each answer it, so it makes one kind of product. Abstract Factory: an object, IBreakfastKitchen, has several creation methods, MakeDrink and MakeMain, and is implemented by ContinentalKitchen and EnglishKitchen, so it makes a whole matching family."
>

An Abstract Factory is often built from several factory methods, one per product. What sets it apart is that the kitchen is an object the client is <Key>handed</Key>, not a method the creator's own base class overrides.

### What a new product kind costs

Abstract Factory makes a new family cheap, and a new kind of product expensive. The interface lists every kind of product, so adding a kind changes the interface and every kitchen that implements it.

If new kinds of product arrive often and new families rarely, this pattern is the wrong shape. It pays off when the kinds are stable and the families are what change.

### Who chooses the kitchen

Somebody has to write `new ContinentalKitchen()` once. That is fine at the edge of a program: its startup code, a configuration setting or a dependency injection registration. The rest of the code receives an <Role kind="contract">IBreakfastKitchen</Role> and never learns which one it is.

### Pitfalls

<Pitfall title="Returning concrete types from the kitchen">

If `MakeDrink` returns `Coffee`, every caller depends on the concrete class again, and a different kitchen cannot return a `Tea`. Declare each creation method with the product interface.

<CodePair
  bad="public Coffee MakeDrink() => new Coffee();"
  good="public IDrink MakeDrink() => new Coffee();"
  badLabel="names the class"
  goodLabel="names the interface"
/>

</Pitfall>

<Pitfall title="One kitchen that switches on the family">

A single kitchen with a flag brings the first version back: two `switch` blocks that can drift apart. Keep one kitchen class per family, so each family lives in exactly one place.

<CodePair
  bad={"public IMain MakeMain() =>\n  english ? new FryUp() : new Croissant();"}
  good="public IMain MakeMain() => new FryUp();"
  badLabel="a flag again"
  goodLabel="one class per family"
/>

</Pitfall>

<Pitfall title="A factory for a family of one">

If the kitchen has a single creation method, nothing has to match anything. You have a Factory Method in a larger box, and a function that makes the drink is lighter.

<CodePair
  bad={"interface IBreakfastKitchen {\n  IDrink MakeDrink();\n}"}
  good="Func<IDrink> makeDrink"
  badLabel="a family of one"
  goodLabel="just a function"
/>

</Pitfall>
