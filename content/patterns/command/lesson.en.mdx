<Section id="problem">

A playlist editor has buttons to add a song, remove a song, and undo. The first version lets the buttons do the work, and remembers the last thing that was done so that Undo can reverse it:

<AnnotatedCode
  caption="The first version: undo is a switch on the last action"
  code={`
public class PlaylistEditor
{
    private readonly Playlist playlist = new();
    private string lastAction = "";
    private string lastTitle = "";
    private int lastIndex;

    public void AddClicked(string title)
    {
        playlist.Add(title);
        lastAction = "add";
        lastTitle = title;
    }

    public void RemoveClicked(int index)
    {
        lastTitle = playlist.RemoveAt(index);
        lastAction = "remove";
        lastIndex = index;
    }

    public void UndoClicked()
    {
        switch (lastAction)
        {
            case "add":
                playlist.RemoveAt(playlist.Count - 1);
                break;
            case "remove":
                playlist.Insert(lastIndex, lastTitle);
                break;
        }
    }
}
`}
  marks={[
    { line: 4, tone: 'bad', badge: '1' },
    { line: 5, tone: 'bad' },
    { line: 6, tone: 'bad' },
    { line: 11, tone: 'bad', badge: '2' },
    { line: 24, tone: 'bad', badge: '3' },
    { line: 26, tone: 'bad' },
    { line: 27, tone: 'bad' },
    { line: 29, tone: 'bad' },
    { line: 30, tone: 'bad' },
  ]}
/>

It works for one click, but <Key>an action is only a name and a few loose fields</Key>. The editor cannot hold an action, so it cannot do much with it:

<BadgeList tone="bad" count={3}>

1. The editor keeps loose fields, one for each thing Undo might need. A move would need two more, and a rename another.
2. Only the last action is remembered. Add two songs, and the first one is overwritten, so Undo can go back one step and no more.
3. Undo is a `switch` that knows every action. A new button needs a new `case`, and a new field to go with it.
4. An action cannot be queued, logged or replayed, because it is not a thing. It is a line in a method.

</BadgeList>

<KeyIdea>

A request can be an object. Make each action a small object that knows how to do itself and how to undo itself, and keep a list of them.

</KeyIdea>

</Section>

A command is an order slip in code: a button makes an <Role kind="concrete">AddSong</Role> edit, the <Role kind="primary">EditHistory</Role> carries it out and keeps it, and the edit knows how to undo itself.

The **command** is <Role kind="contract">IPlaylistEdit</Role>, an interface with two methods, `Do` and `Undo`.

The **concrete commands** are <Role kind="concrete">AddSong</Role>, <Role kind="concrete">RemoveSong</Role> and <Role kind="concrete">MoveSong</Role>. Each one holds the playlist and what it needs to do its job, and each knows how to reverse itself. <Role kind="concrete">RemoveSong</Role> keeps the title it removed, because without it nobody could put the song back.

The **receiver** is <Role kind="concrete">Playlist</Role>. It does the real work, with `Insert`, `RemoveAt` and `Move`. It knows nothing about edits.

The **invoker** is <Role kind="primary">EditHistory</Role>. `Run` does an edit and puts it on a stack. `Undo` takes the last edit off the stack and asks it to undo itself.

<Section id="example">

The example adds three songs, moves one, removes one, and undoes twice. Run it and you should see seven lines: `add Blue Monday: Blue Monday`, `add Heroes: Blue Monday, Heroes`, `add Starman: Blue Monday, Heroes, Starman`, `move Starman to the top: Starman, Blue Monday, Heroes`, `remove song 2: Starman, Heroes`, then `undo: Starman, Blue Monday, Heroes` and `undo: Blue Monday, Heroes, Starman`. The last two undos went back through the remove and the move, in reverse order.

Then change it. Add a `RenamePlaylist` edit. Give <Role kind="concrete">Playlist</Role> a property `public string Name { get; set; } = "Mix";`. Write `RenamePlaylist(Playlist playlist, string newName)`, a class that implements <Role kind="contract">IPlaylistEdit</Role>. It keeps the old name when `Do` runs, so that `Undo` can put it back. At the end of the example, add `history.Run(new RenamePlaylist(playlist, "Road trip"));` and `Console.WriteLine(playlist.Name);`, then `history.Undo();` and the same `Console.WriteLine` again. You should see `Road trip` and then `Mix`, after the seven lines as before. <Key>A new kind of edit is a new class</Key>: <Role kind="primary">EditHistory</Role> needs no change.

<Section id="when-to-use">

Use Command when:

<Checklist>
  <Verdict ok><span>you need to <Key>undo</Key> actions, or redo them, and each action knows how to reverse itself;</span></Verdict>
  <Verdict ok><span>requests should be <Key>kept, queued or logged</Key>, to run later, run again, or be written to a file;</span></Verdict>
  <Verdict ok><span>the code that asks for the work should <Key>not know what the work is</Key>, as with a button, a menu item and a shortcut that all do the same thing.</span></Verdict>
  <Verdict ok={false}><span>**Skip it** when a plain method call is enough. If nothing is undone, queued or logged, an object for every call is only more classes to read.</span></Verdict>
</Checklist>

### Undo is a stack

Many undos come from one small idea: a stack. Every edit that is run goes on top. Undo takes the top one off and reverses it, so the newest edit is always the first to go.

<Figure
  caption="The stack of done edits"
  description="A stack of three done edits. The top is the newest, a RemoveSong, and it is undone first. Under it is a MoveSong, and at the bottom an AddSong, the oldest, which is undone last."
>
<Stack align="stretch">
<ColumnHead>Done edits</ColumnHead>

<Box role="concrete" mono={false}>MoveSong</Box>

</Stack>

<Note icon="lightbulb">

Redo is the same idea with a second stack. When an edit is undone, it moves to the redo stack, and Redo runs it again. A new edit clears the redo stack.

</Note>

### Pitfalls

<Pitfall title="An edit that keeps too little">

Undo can only put back what the edit remembers. A `RemoveSong` that only keeps the index knows where the song was, but not which song it was, and when Undo runs, the title is gone. Have the edit keep, when `Do` runs, everything its `Undo` will need.

<CodePair
  bad={"public void Do() => playlist.RemoveAt(index);\npublic void Undo() { /* which song? */ }"}
  good={"public void Do() => removed = playlist.RemoveAt(index);\npublic void Undo() => playlist.Insert(index, removed);"}
  badLabel="the removed title is lost"
  goodLabel="the edit keeps what Undo needs"
/>

</Pitfall>

<Pitfall title="A history that looks inside the edits">

The history should treat every edit the same. If it checks the kind of edit, it has taken back the knowledge that the edits were meant to hold, and every new edit means a change in the history again.

<CodePair
  bad={"if (edit is AddSong add)\n    playlist.Insert(playlist.Count, add.Title);\nelse if (edit is MoveSong move) ..."}
  good={"edit.Do();\ndone.Push(edit);"}
  badLabel="the history knows each edit"
  goodLabel="the history only calls Do"
/>

</Pitfall>
