<Section id="problem">

A cinema ticket form has a film picker, a showtime picker, a seat picker, a student checkbox and a price label. Picking a film changes the showtimes, a showtime changes the free seats, and seats and the student box both change the price. The first version lets each widget call the ones it affects:

<AnnotatedCode
  caption="The first version: every widget calls the others"
  code={`
public class FilmPicker
{
    public ShowtimePicker Showtimes;
    public SeatPicker Seats;
    public PriceLabel Price;

    public void Pick(string title)
    {
        Showtimes.Offer(title);
        Seats.SetFree(0);
        Price.Show(0);
    }
}

public class SeatPicker
{
    public int Count;
    public PriceLabel Price;
    public StudentBox Student;

    public void Pick(int count)
    {
        Count = count;
        Price.Show(count * (Student.IsOn ? 7 : 10));
    }
}

public class StudentBox
{
    public bool IsOn;
    public PriceLabel Price;
    public SeatPicker Seats;

    public void Set(bool on)
    {
        IsOn = on;
        Price.Show(Seats.Count * (on ? 7 : 10));
    }
}
`}
  marks={[

<BadgeList tone="bad" count={3}>

1. Each widget holds references to several others. Four widgets and a label make a web, and every new widget has to be wired into it.
2. `FilmPicker` knows what the others must do when a film changes: offer showtimes, clear the seats, clear the price. Each rule about the form is spread over the widgets.
3. The price rule is written twice, in `SeatPicker` and in `StudentBox`. Change the student price in one and forget the other, and the form shows two different prices.
4. No widget can be used alone. `FilmPicker` cannot be built or tested without a showtime picker, a seat picker and a price label, and a new snack-combo checkbox means opening several widgets.

</BadgeList>

<KeyIdea>

Take the rules about who reacts out of the widgets. Let each widget say only that it changed, and let one object decide what happens next.

</KeyIdea>

</Section>

<Section id="structure">

Mediator has an interface for the mediator, the class that implements it, and the widgets that talk to it. The widgets know the interface, and the form knows the widgets.

<Figure
  caption="Widgets, a contract and a form"
  description="Four widgets, FilmPicker, ShowtimePicker, SeatPicker and StudentBox, tell ITicketForm that they changed. TicketForm implements ITicketForm, and it builds the widgets and decides who reacts."
>
<Row align="start">
<Stack align="stretch">
<ColumnHead>The widgets</ColumnHead>
<Box role="concrete" mono={false}>FilmPicker</Box>
<Box role="concrete" mono={false}>ShowtimePicker</Box>
<Box role="concrete" mono={false}>SeatPicker</Box>
<Box role="concrete" mono={false}>StudentBox</Box>
</Stack>
<Arrow label="tell" />
<Stack align="stretch">
<ColumnHead>The mediator contract</ColumnHead>
<Box role="contract" mono={false} sub="Changed">ITicketForm</Box>
</Stack>
<Arrow label="implemented by" />
<Stack align="stretch">
<ColumnHead>The form</ColumnHead>
<Box role="primary" mono={false} sub="decides who reacts">TicketForm</Box>
</Stack>
</Row>
</Figure>

The **mediator** is <Role kind="contract">ITicketForm</Role>, an interface with one method, `Changed`. A widget calls it with itself.

The **concrete mediator** is <Role kind="primary">TicketForm</Role>. It builds the widgets, gives each one itself, and holds the rules. When `Changed` is called, it looks at which widget it was and tells the others what to do.

The **colleagues** are `FilmPicker`, `ShowtimePicker`, `SeatPicker`, `StudentBox` and `PriceLabel`. Each of the first four takes an <Role kind="contract">ITicketForm</Role> in its constructor, and calls `Changed(this)` after it changes. None of them knows another widget. `PriceLabel` only shows what it is told, so it does not need the form at all.

Here the form is handed to the widgets in their constructors. A setter works too. The interface is useful when more than one form can use the same widgets.

<Section id="example">

The example builds a ticket form, picks the film Dune, the 20:00 show and two seats, and then switches on the student ticket. Run it and you should see four lines: `showtimes: 18:00, 20:00`, `free seats: 6`, `price: 20 EUR` and `student price: 14 EUR`. Dune offers two showtimes, the 20:00 show has six free seats, two seats cost 10 each, and a student pays 7 each. <Role kind="primary">TicketForm</Role> made every one of those decisions, and no widget called another.

Then change it. Add a snack-combo checkbox that costs 5 EUR for each seat. Write `public class ComboBox(ITicketForm form)`, a class like `StudentBox`: it has `public bool IsOn { get; private set; }` and a `Set(bool on)` method that stores the value and calls `form.Changed(this)`. In <Role kind="primary">TicketForm</Role>, add the property `public ComboBox Combo { get; }`, create it in the constructor with `Combo = new(this);`, and change the last line of `Changed` to `Price.Show(Seats.Count * ((Student.IsOn ? 7 : 10) + (Combo.IsOn ? 5 : 0)));`. After the last `Console.WriteLine` line at the top of the example, and before the first type declaration, add `form.Combo.Set(true);` and `Console.WriteLine($"with combo: {form.Price.Text}");`. You should see `with combo: 24 EUR` after the four lines as before. <Key>A new widget is a new class and one rule in the form</Key>: the other widgets need no change.

<Section id="when-to-use">

Use Mediator when:

<Checklist>
  <Verdict ok><span>several objects <Key>change each other</Key>, and the references between them have become a web;</span></Verdict>
  <Verdict ok><span>the rules about <Key>who reacts to what</Key> belong together, and change together;</span></Verdict>
  <Verdict ok><span>you want to <Key>reuse the parts</Key> in another form, without taking the others with them.</span></Verdict>
  <Verdict ok={false}><span>**Skip it** when only one object reacts to another. A direct call is shorter and easier to follow than a mediator.</span></Verdict>
</Checklist>

### Mediator or observer

Both let one object change without knowing who reacts. The difference is who decides, and whether they talk back.

Both stand between classes. The difference is which way the calls go.

### Pitfalls

<Pitfall title="The mediator grows into a god object">

All the rules are in one place, and that place can grow. If the form also works out prices, discounts and every other detail, it becomes the one class nobody dares to touch. Keep in the mediator the rules about who reacts to whom, and give the work itself to its own class.

<CodePair
  bad={"var price = Seats.Count * (Student.IsOn ? 7 : 10);\nif (Showtime.Time == \"20:00\") price += 2 * Seats.Count;\nif (Film.Title == \"Dune\") price -= 1;\nif (Seats.Count > 4) price = price * 9 / 10;\nPrice.Show(price);"}
  good={"Price.Show(rules.Total(\n    Film.Title, Showtime.Time, Seats.Count, Student.IsOn));"}
  badLabel="every pricing rule in the form"
  goodLabel="the form only asks a price class"
/>

</Pitfall>

<Pitfall title="Widgets that still call each other">

If one widget keeps a reference to another "just this once", the web starts to grow back, and the form is no longer the only place that knows the rules.

<CodePair
  bad={"public void Pick(int count)\n{\n    Count = count;\n    price.Show(count * 10);\n}"}
  good={"public void Pick(int count)\n{\n    Count = count;\n    form.Changed(this);\n}"}
  badLabel="the widget updates the price itself"
  goodLabel="the widget only says it changed"
/>

</Pitfall>
