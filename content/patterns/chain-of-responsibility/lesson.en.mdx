<Section id="problem">

A company pays back its staff's expenses, and the amount decides who has to approve a claim. The first version puts all the rules in the form:

<AnnotatedCode
  caption="The first version: one method knows every approver"
  code={`
public class ExpenseForm
{
    public string Submit(decimal amount)
    {
        if (amount <= 100)
            return $"{amount} EUR is approved by the team lead";
        else if (amount <= 1000)
            return $"{amount} EUR is approved by the department head";
        else if (amount <= 10000)
            return $"{amount} EUR is approved by the finance director";
        else
            return $"{amount} EUR is refused";
    }
}
`}
  marks={[
    { line: 5, tone: 'bad', badge: '1' },
    { line: 6, tone: 'bad' },
    { line: 7, tone: 'bad', badge: '2' },
    { line: 8, tone: 'bad' },
    { line: 9, tone: 'bad' },
    { line: 10, tone: 'bad' },
    { line: 11, tone: 'bad', badge: '3' },
    { line: 12, tone: 'bad' },
  ]}
/>

It gives the right answer today, but <Key>the form itself decides who approves what</Key>. The team lead, the department head and the finance director do not exist as things of their own. They are lines in a ladder:

<BadgeList tone="bad" count={3}>

1. The form knows every approver and every limit. A new limit for the department head means opening `ExpenseForm`.
2. The order of the branches is the rule. Put the 1,000 check above the 100 check, and a claim of 60 EUR goes to the department head.
3. A new step means editing the ladder, and the ladder grows with every step. Adding a travel desk that approves small claims first is a change in the middle of this method.
4. Another kind of request, such as a purchase order, cannot use the ladder. It would need a copy of it.

</BadgeList>

<KeyIdea>

The sender should not have to know who will deal with its request. Put each approver in its own object, link them in a line, and let a claim travel along it.

</KeyIdea>

</Section>

The **handler** is <Role kind="contract">Approver</Role>, an abstract class. It holds the link to the next approver, `SetNext` to join one on, and `Handle`, which each approver implements. It also has a small helper, `Pass`, which sends a claim to the next approver, or gives the default answer when there is none.

The **concrete handlers** are <Role kind="concrete">TeamLead</Role>, <Role kind="concrete">DepartmentHead</Role> and <Role kind="concrete">FinanceDirector</Role>. Each one has a limit. Within it, the approver approves the claim and stops. Above it, the approver calls `Pass`.

The client is <Role kind="concrete">ExpenseForm</Role>. It holds the first approver and calls its `Handle`. The chain itself is put together outside the form, with `SetNext`, so changing the chain means changing no approver and not the form.

<Section id="example">

The example builds the chain with `SetNext` and sends four claims through it. Run it and you should see four lines: `60 EUR is approved by the team lead`, `800 EUR is approved by the department head`, `4000 EUR is approved by the finance director` and `25000 EUR is refused: nobody can approve it`. Each claim stopped at the first approver who could take it.

Then change it. Add a travel desk in front of the team lead. Write `TravelDesk`, a new class in the same style as <Role kind="concrete">TeamLead</Role>, that approves claims up to 30 EUR, and passes the rest with `Pass`. Before the form is made, create one with `var desk = new TravelDesk();` and link it with `desk.SetNext(teamLead);`, then give `desk` to the form instead of `teamLead`. Add a claim of `20m` to the list. You should see `20 EUR is approved by the travel desk`, and the other four lines as before. <Key>A new link is one new class and one line of wiring</Key>: <Role kind="concrete">ExpenseForm</Role> and the other approvers need no change.

<Section id="when-to-use">

Use Chain of Responsibility when:

<Checklist>
  <Verdict ok><span>a request can be handled by <Key>one of several objects</Key>, and the sender should not have to know which one;</span></Verdict>
  <Verdict ok><span>the handlers and their <Key>order may change</Key>, or may be different in different places, and you want to change them without touching the sender;</span></Verdict>
  <Verdict ok><span>each handler can <Key>decide for itself</Key> whether the request is its own, using only the request.</span></Verdict>
  <Verdict ok={false}><span>**Skip it** when there are only two or three fixed cases that never change. A plain `if` is simpler than a chain, and when every request must go to one known handler, call that handler directly.</span></Verdict>
</Checklist>

### Chain or decorator

Both patterns link objects in a line and pass a call along. They differ in what the line is for.

### A chain you already use

<Note icon="lightbulb">

ASP.NET Core's middleware is a chain. Each piece of middleware gets the request and a `next` delegate. It can answer by itself, as an authorisation check does when it returns 401, or call `next` to hand the request on. A piece that does its work and then also calls `next` is closer to a pipeline of decorators, which is fine when that is what you want. Keep the two ideas apart when you design: does the request stop at one handler, or does it go through all of them?

</Note>

### Pitfalls

<Pitfall title="A claim that falls off the end">

If the last approver passes a claim on and nobody is next, something has to answer. Without a default, the caller gets a `null`, or an exception, or silence, and a refused claim looks the same as a lost one. Let the end of the chain answer on purpose, in <Role kind="contract">Approver</Role>, so that every link gets it for free.

<CodePair
  bad={"protected string? Pass(decimal amount) =>\n    next?.Handle(amount);   // null for 25,000"}
  good={"protected string Pass(decimal amount) =>\n    next?.Handle(amount) ?? $\"{amount} EUR is refused\";"}
  badLabel="nothing at the end of the chain"
  goodLabel="the end gives a default answer"
/>

</Pitfall>

<Pitfall title="An approver that forgets to pass on">

A link that does not approve a claim must pass it. If it returns an empty answer instead, the claim stops there and the links after it are never reached. The chain looks right, and a claim above the limit quietly gets no answer.

<CodePair
  bad={"public override string Handle(decimal amount) =>\n    amount <= 100 ? \"approved by the team lead\" : \"\";"}
  good={"public override string Handle(decimal amount) =>\n    amount <= 100 ? \"approved by the team lead\" : Pass(amount);"}
  badLabel="the claim stops here"
  goodLabel="the claim goes to the next link"
/>

</Pitfall>
