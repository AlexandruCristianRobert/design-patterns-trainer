<Section id="problem">

An evening-class school enrols students through four classes. <Role kind="concrete">SeatRegister</Role> holds a place in the course, <Role kind="concrete">PaymentGateway</Role> takes the fee, <Role kind="concrete">LearnerAccounts</Role> adds the course to the student's account, and <Role kind="concrete">WelcomeMailer</Role> sends the welcome mail. There are two ways to enrol: the sign-up page and the phone-booking screen. The first version gives each of them all four classes:

<AnnotatedCode
  caption="The first version: every client runs the four steps itself"
  code={`

That costs you in several ways:

<BadgeList tone="bad" count={3}>

1. The same four calls are written twice. `SignUpPage.Submit` and `PhoneBooking.Book` have identical bodies, and a third way to enrol, such as a mobile app, would copy them a third time.
2. The order is a rule that nothing enforces. A seat should be reserved before anyone is charged, but `Charge` before `Reserve` compiles just as well, and one careless copy could charge a student for a seat they did not get.
3. Every client depends on four classes. Each constructor takes all four, so a new step, such as a text message, has to be added to every client, and a change to one subsystem can reach all of them.
4. Every test of a client has to build all four subsystems first.

</BadgeList>

<KeyIdea>

Enrolling a student is one thing to the caller, and four steps to the school. The steps belong in one place, not in every client.

</KeyIdea>

</Section>

The **facade** is <Role kind="primary">EnrolmentDesk</Role>. It holds the four subsystems and has one method, `Enrol`, that calls them in order. It is the only class the clients need to know.

The **subsystems** are <Role kind="concrete">SeatRegister</Role>, <Role kind="concrete">PaymentGateway</Role>, <Role kind="concrete">LearnerAccounts</Role> and <Role kind="concrete">WelcomeMailer</Role>. They do the real work, and they have never heard of the desk: they take no part in the pattern except by being called.

The facade <Key>adds no new features</Key>. Every step happens in a subsystem, and the desk only decides which to call and in what order. The clients, `SignUpPage` and `PhoneBooking`, now know one class instead of four.

<Section id="example">

The example is the program from the scene. Run it and you should see four lines, one per step: `Reserved a seat in Pottery`, `Charged Ana for Pottery`, `Added Pottery to Ana's account` and `Welcome mail for Pottery sent to Ana`. The page made one call to get all four.

Then change it. Add a text-message reminder: a class `SmsReminder` with a `Send(student, course)` method that prints a line, given to <Role kind="primary">EnrolmentDesk</Role> with its other subsystems, and called as a fifth step at the end of `Enrol`. You should not need to touch `SignUpPage`, which is the point: <Key>a new step is added in one place</Key>.

Note that `Enrol` is the only place that lists the steps. In the first version, the same change would have been made in two clients.

<Section id="when-to-use">

Use Facade when:

<Checklist>
  <Verdict ok><span>a job takes <Key>several classes called in the right order</Key>, and every client repeats the same calls;</span></Verdict>
  <Verdict ok><span>you want clients to depend on <Key>one simple interface</Key> instead of the details of a subsystem, so the subsystem can change behind it;</span></Verdict>
  <Verdict ok><span>you want to layer a system, with one entry point for each layer, so the parts behind it can be used on their own as well.</span></Verdict>
  <Verdict ok={false}><span>**Skip it** when there is only one client and one or two classes behind it. A class that forwards every call to a single object is only one more name to learn.</span></Verdict>
</Checklist>

### Facade or Adapter

Both put a class in front of other classes, and they are easy to confuse. The difference is the reason: an adapter makes one thing fit an interface somebody already expects, and a facade simplifies many things behind an interface of its own.

### Pitfalls

<Pitfall title="A desk that becomes a god object">

It is tempting to put one more thing in the desk: who may enrol, a discount, a waiting list. Soon <Role kind="primary">EnrolmentDesk</Role> holds the school's rules as well as its steps. It is no longer a simple front door but a large class that every change touches, and you have moved the tangle, not removed it. Keep the desk to calling the steps. A rule belongs in a class of its own or in the subsystem it is about.

<CodePair
  bad={"public void Enrol(string student, string course)\n{\n    if (student.EndsWith(\"(staff)\")) return;   // a rule\n    seats.Reserve(course);\n    payments.Charge(student, course);\n    // ...and a discount, a waiting list..."}
  good={"// The rule is in a class of its own.\npublic bool Allows(string student) => !student.EndsWith(\"(staff)\");\n\n// The desk only calls the steps, in order.\nseats.Reserve(course);\npayments.Charge(student, course);"}
  badLabel="the desk decides things"
  goodLabel="the desk only calls"
/>

</Pitfall>
