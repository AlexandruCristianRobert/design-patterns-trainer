<Section id="problem">

A greenhouse controller reads rules that the gardener writes as text, such as `soil-dry and not raining`. The first version takes the text apart by hand:

<AnnotatedCode
  caption="The first version: every rule shape is a branch"
  code={`
public class Controller
{
    public bool ShouldAct(string rule, Readings readings)
    {
        var words = rule.Split(' ');
        if (words.Length == 1)
            return readings.Has(words[0]);
        if (words.Length == 2 && words[0] == "not")
            return !readings.Has(words[1]);
        if (words.Length == 3 && words[1] == "and")
            return readings.Has(words[0]) && readings.Has(words[2]);
        if (words.Length == 4 && words[1] == "and" && words[2] == "not")
            return readings.Has(words[0]) && !readings.Has(words[3]);
        return false;
    }
}
`}
  marks={[
    { line: 5, tone: 'bad', badge: '1' },
    { line: 6, tone: 'bad', badge: '2' },
    { line: 8, tone: 'bad' },
    { line: 10, tone: 'bad' },
    { line: 12, tone: 'bad', badge: '3' },
    { line: 14, tone: 'bad' },
  ]}
/>

It works for the four shapes it knows, but <Key>the language is hidden in string splitting</Key>. The code does not say what a rule is, so it cannot grow:

<BadgeList tone="bad" count={3}>

1. The text is split on spaces by hand, so the code and the grammar are mixed up in the same few lines.
2. There is one `if` for every shape of rule. A rule with `or`, or a second `and`, needs a new branch and a new guess about the word count.
3. Rules cannot hold other rules. `and not` has its own branch because `not` cannot be put inside `and`, so `not (soil-wet or raining)` has no place at all.
4. A rule that does not fit any branch quietly falls through to `return false`, and nobody is told.

</BadgeList>

<KeyIdea>

A rule can be a class. Make one small class for each kind of rule, and let a sentence be a tree of them that can answer for itself.

</KeyIdea>

</Section>

The **expression** is <Role kind="contract">IRule</Role>, an interface with one method, `IsTrue`.

The **terminal expression** is <Role kind="concrete">SensorIs</Role>. It holds a sensor name and asks the readings for it. It holds no other rule, so a branch of the tree ends here.

The **nonterminal expressions** are <Role kind="primary">Both</Role>, <Role kind="primary">Either</Role> and <Role kind="primary">Not</Role>. Each one holds other rules and puts their answers together: `and`, `or`, or the opposite.

The **context** is <Role kind="concrete">Readings</Role>, the set of sensors that are on right now. It is passed down the tree on every question.

<Section id="example">

The example builds two rules, `water` for `soil-dry and not raining` and `vent` for `hot and sunny`, and asks each of them about three days of readings. Run it and you should see three lines: `morning: water yes, vent no`, `noon: water yes, vent yes` and `storm: water no, vent no`. The same two trees answered all three days.

Then change it. Add an `Either` rule for frost. After the `vent` line, add `var frost = new Either(new SensorIs("frost"), new SensorIs("snow"));`. Add a fourth day, `("night", new Readings("frost"))`, to the `days` list. Then change the `WriteLine` to print `, frost {Answer(frost.IsTrue(readings))}` after the vent. You should see `night: water no, vent no, frost yes`, and the first three lines now end with `, frost no`. <Key>A new rule is a new tree</Key>: the classes <Role kind="primary">Both</Role> and <Role kind="primary">Either</Role> needed no change.

<Section id="when-to-use">

Use Interpreter when:

<Checklist>
  <Verdict ok><span>you have <Key>a small, stable language</Key>, such as a few kinds of rule, filter or formula, written as sentences;</span></Verdict>
  <Verdict ok><span>a sentence should be <Key>built once and asked many times</Key>, against different facts;</span></Verdict>
  <Verdict ok><span>rules should <Key>nest</Key>, so that a rule can hold a rule, as with `and`, `or` and `not`.</span></Verdict>
  <Verdict ok={false}><span>**Skip it** when the language is large or changes often. Dozens of grammar rules mean dozens of classes, and a parser generator does the job better.</span></Verdict>
</Checklist>

### Interpreter or composite

The two have the same shape: a tree where every node is used through one interface, and some nodes hold other nodes. What differs is what the tree is for.

### Parsing is a separate step

In the example, the trees are built in code. A gardener who types `soil-dry and not raining` needs one more piece, a parser, that reads the text and builds the tree. Interpreter is about what the tree does once it exists.

>

<Note icon="lightbulb">

For a small language, a short parser by hand is fine. For a large one, use a parser generator, which writes it for you from a description of the grammar.

</Note>

### Pitfalls

<Pitfall title="A grammar that is too big">

Every grammar rule is a class. Ten rules are ten small classes, which is readable. A programming language is hundreds, and the tree-walking code becomes slow and hard to follow. Keep the language small, or use a parser generator or a language that exists already.

<CodePair
  bad={"class WhileLoop : IExpression { ... }\nclass SwitchCase : IExpression { ... }\nclass Lambda : IExpression { ... }\n// ...and 60 more"}
  good={"// four rules: sensor, and, or, not\nIRule rule = RuleParser.Parse(text);"}
  badLabel="a whole language, by hand"
  goodLabel="a small language, kept small"
/>

</Pitfall>

<Pitfall title="Parsing inside the rules">

A rule should answer `IsTrue` from the tree it holds. If it splits text to find out what it is, then the parsing is back inside the evaluating, and the classes are no better than the first version.

<CodePair
  bad={"public bool IsTrue(Readings r)\n{\n    var words = text.Split(' ');\n    return r.Has(words[0]) && ...;\n}"}
  good={"public bool IsTrue(Readings r) =>\n    left.IsTrue(r) && right.IsTrue(r);"}
  badLabel="the rule parses its own text"
  goodLabel="the rule asks the rules it holds"
/>

</Pitfall>
