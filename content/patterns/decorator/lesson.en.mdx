<Section id="problem">

A video player shows subtitles. Most lines are shown as they are, some need the speaker's name in front, and shouted lines appear in capitals. The first version usually adds one subclass per kind of caption:

<AnnotatedCode
  caption="The first version: a class for every combination"
  code={`
public class Caption
{
    public virtual string Render(string line) => line;
}

public class SpeakerCaption(string speaker) : Caption
{
    public override string Render(string line) => $"{speaker}: {line}";
}

public class UppercaseCaption : Caption
{
    public override string Render(string line) => line.ToUpperInvariant();
}

// A shouted line with a speaker needs a third class.
public class UppercaseSpeakerCaption(string speaker) : Caption
{
    public override string Render(string line) => $"{speaker}: {line}".ToUpperInvariant();
}
`}
  marks={[
    { line: 16, tone: 'bad', badge: '1' },
    { line: 17, tone: 'bad', badge: '2' },
    { line: 18, tone: 'bad' },
    { line: 19, tone: 'bad', badge: '3' },
    { line: 20, tone: 'bad' },
  ]}
/>

It works, but <Key>every combination is a class of its own</Key>, and that hurts in several ways:

<BadgeList tone="bad" count={3}>

1. Each new feature doubles the number of classes. Add italics for off-screen voices and you also need italic with speaker, italic in capitals, and all three at once.
2. The combination is fixed when you write the code. A viewer who turns speaker names off in the settings cannot remove them from an object that was built with them.
3. The same logic is copied. `UppercaseSpeakerCaption` repeats what the other two classes already do, so a change to the name format has to be made twice.
4. Which feature comes first is buried inside each class. Should the name be in capitals too? Every combined class answers that question again.

</BadgeList>

<KeyIdea>

Showing a line is the caption's job. Each extra feature is a small job of its own, and you want to add them one at a time and in any combination.

</KeyIdea>

Decorator has the same shape: a decorator has the same interface as the object it wraps and passes the work on to it, adding its own part before or after. Because a decorated object still looks like the original, you can wrap it again.

<KeyIdea>

A decorator has the same interface, <Role kind="contract">ICaption</Role>, as the object it wraps, passes the work on to it and adds its own part.

</KeyIdea>

The **component** is that interface, here <Role kind="contract">ICaption</Role>, with its one method, <Role kind="contract">Render</Role>. The concrete component, <Role kind="concrete">PlainCaption</Role>, does the basic job and knows nothing about decorators.

The **decorator** implements the same interface and holds a reference to another <Role kind="contract">ICaption</Role>. Here the base class <Role kind="primary">CaptionDecorator</Role> keeps that reference and forwards <Role kind="contract">Render</Role> by default; concrete decorators such as <Role kind="concrete">SpeakerTag</Role> and <Role kind="concrete">Uppercase</Role> override it to add their part.

Look at the two lines from <Role kind="primary">CaptionDecorator</Role> up to <Role kind="contract">ICaption</Role>. The dashed one with the hollow arrowhead says the decorator implements <Role kind="contract">ICaption</Role>; the solid one labelled `decorates 1` says it also holds one, the caption it decorates. It is a caption and has a caption. Because the field's type is the interface and not <Role kind="concrete">PlainCaption</Role>, a decorator can wrap another decorator as easily as a plain caption. <Section id="when-to-use">

Use Decorator when:

<Checklist>
  <Verdict ok><span>you want to <Key>add features to single objects at runtime</Key>, without changing their class or every other object of that class;</span></Verdict>
  <Verdict ok><span>features can be combined freely, and a subclass for every combination would multiply out of control;</span></Verdict>
  <Verdict ok><span>a class is sealed or comes from a library, so you cannot extend it by inheritance, but you can wrap it behind an interface it implements.</span></Verdict>
  <Verdict ok={false}><span>**Skip it** when there is only one fixed combination. A single class, or one optional setting, is easier to follow than a stack of wrappers.</span></Verdict>
</Checklist>

### Stacking order

Decorators do not commute. Here the decorators work after the inner call, so the outer one runs last and sees, and can change, everything the inner ones produced. Our example shows it in the text: <Role kind="concrete">Uppercase</Role> outside <Role kind="concrete">SpeakerTag</Role> gives `ANA:`, inside it gives `Ana:`. With caching and logging the order decides whether a cache hit is logged; with retries and timeouts it decides whether the timeout covers one attempt or all of them.

### Streams in .NET

The best-known decorators in .NET are streams. `BufferedStream` wraps any `Stream` and adds a buffer; `GZipStream` wraps any `Stream` and compresses or decompresses what passes through. Both are themselves a `Stream`, so you can write `new GZipStream(new BufferedStream(file), CompressionMode.Compress)` and hand the result to code that only knows `Stream`. Order applies here too: a buffer under the compressor batches the compressed bytes written to the file; a buffer above it batches the small writes going into the compressor. (The trainer's runtime has no file or stream support, so the exercises use their own interfaces instead.)

### Pitfalls

<Pitfall title="Identity and equality break">

A decorated object is a different object from the one inside it. `shouted == plain` is false, a `HashSet` of captions treats them as two items, and a type check such as `caption is PlainCaption` fails on a wrapped one. Code that compares objects or checks their concrete type does not work well with decorators; let it depend on the interface only.

<CodePair
  bad="if (caption is PlainCaption) { … }"
  good="void Show(ICaption caption) { … }"
  badLabel="fails on a wrapped one"
  goodLabel="depends on the interface only"
/>

</Pitfall>

<Pitfall title="Long wrapper chains are hard to debug">

Ten small layers each doing one thing read well in code but badly in a stack trace or debugger, where you step through every forwarding call to find the one that changed the result. Keep chains short, give each decorator one clear job, and make the stack visible where it is built.

<CodePair
  bad="new A(new B(new C(new D(new E(plain)))))  // repeated in several places"
  good="var caption = CaptionStacks.ForShouting(plain);"
  badLabel="long chain, built in several places"
  goodLabel="short stack, built in one named place"
/>

</Pitfall>

<Pitfall title="Confusing Decorator with inheritance">

A decorator also overrides <Role kind="contract">Render</Role>, so it is easy to think of it as a subclass. The difference is that a subclass changes a class for every object, once, at compile time, while a decorator changes one object at runtime and can be stacked or removed. Here the decorators inherit from <Role kind="primary">CaptionDecorator</Role> only to share the forwarding code; the behavior comes from the object they wrap, not from a parent class.

<CodePair
  bad="class ShoutCaption : Caption { … }"
  good="ICaption shouted = new Uppercase(plain);"
  badLabel="subclass changes the class"
  goodLabel="decorator wraps one object at runtime"
/>

</Pitfall>
