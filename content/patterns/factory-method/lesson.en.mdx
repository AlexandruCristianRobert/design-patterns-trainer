<Section id="problem">

A platform game sends waves of enemies at the player. Every level spawns its waves <Key>the same way</Key>, numbering each enemy as it appears, but <Key>the enemies depend on the level</Key>: wolves in the forest, bats in the cave. The first version usually picks the enemy inside the wave logic:

<AnnotatedCode
  caption="The first version: the wave logic also picks the enemy"
  code={`
public class Level(string terrain)
{
    public string SpawnWave(int size)
    {
        var wave = new List<string>();
        for (var i = 1; i <= size; i++)
        {
            IEnemy enemy = terrain switch
            {
                "forest" => new Wolf(),
                "cave" => new Bat(),
                _ => throw new ArgumentException($"Unknown terrain: {terrain}"),
            };
            wave.Add($"{enemy.Name} {i}");
        }
        return string.Join(", ", wave);
    }
}
`}
  marks={[
    { line: 8, tone: 'bad', badge: '1' },
    { line: 9, tone: 'bad' },
    { line: 10, tone: 'bad', badge: '2' },
    { line: 11, tone: 'bad' },
    { line: 12, tone: 'bad', badge: '3' },
    { line: 13, tone: 'bad' },
  ]}
/>

It works, but the class that runs the wave also has to know every enemy, and that hurts in several ways:

<BadgeList tone="bad" count={3}>

1. Adding a desert level with scorpions means editing `SpawnWave`, even though the way a wave is spawned has not changed.
2. <Role kind="primary">Level</Role> names every concrete enemy class with `new`, so it depends on all of them, and so does everything that uses <Role kind="primary">Level</Role>.
3. A typo in the terrain string compiles fine and only fails when a player reaches that level.
4. The same `switch` tends to spread. Boss fights, sound effects and loot drops each pick by terrain too, and each copy has to be kept in step.

</BadgeList>

<KeyIdea>

Spawning a wave is the level's job. Deciding which enemy to make is a second job, and it is the one that differs from level to level.

</KeyIdea>

</Section>

<Section id="analogy">

Think of a delivery company with depots in different places. Head office writes one procedure for every depot: load the parcels, check the route, send the vehicle out. Head office does not say which vehicle. The city depot uses cargo bikes, the mountain depot uses four-wheel-drive vans.

The procedure is the same everywhere and is written once. Only one step, "get a vehicle", is left to each depot, and a new depot can open without anyone rewriting the procedure.

Factory Method has the same shape: a <Role kind="primary">base class</Role> owns the operation and leaves one step, creating an object, to a method that each <Role kind="concrete">subclass</Role> overrides. The <Role kind="primary">base class</Role> works with whatever it gets back through a <Role kind="contract">shared interface</Role>.

The **creator**, here the abstract class <Role kind="primary">Level</Role>, owns the operation that does the real work, `SpawnWave`. It also declares the **factory method**, <Role kind="contract">CreateEnemy</Role>, and calls it whenever it needs a new object. Concrete creators such as <Role kind="concrete">ForestLevel</Role> and <Role kind="concrete">CaveLevel</Role> override only that method.

The created objects share an interface, <Role kind="contract">IEnemy</Role>. Each concrete creator makes its own concrete class: <Role kind="concrete">ForestLevel</Role> creates a <Role kind="concrete">Wolf</Role> and <Role kind="concrete">CaveLevel</Role> creates a <Role kind="concrete">Bat</Role>. The dashed «creates» arrows show who calls `new` on which class.

Look at what <Role kind="primary">Level</Role> points to: only <Role kind="contract">IEnemy</Role>. The base class never names <Role kind="concrete">Wolf</Role> or <Role kind="concrete">Bat</Role>, so a new level is a new subclass and a new enemy class, and `SpawnWave` does not change. Hover or focus a box to see its code in the example.

<Section id="example">

The example is the program from the scene. Run it and you should see two lines: `Forest: wolf 1, wolf 2` and `Cave: bat 1, bat 2`, both from the same `SpawnWave` method.

Then change it. Add a `Scorpion` class that implements `IEnemy`, and a `DesertLevel` that overrides `CreateEnemy` to return one. Spawn a wave in the desert from the top-level code. You should not need to touch `Level`, `ForestLevel` or `CaveLevel`. That is the point of the pattern.

Note that the numbering stays in `SpawnWave`. Everything that is the same for every level belongs in the creator, so no subclass has to repeat it or can get it wrong.

<Section id="when-to-use">

<Checklist>
  <Verdict ok><span>a base class has an operation that needs new objects, but <Key>which class to create depends on the subclass</Key>;</span></Verdict>
  <Verdict ok><span>code is full of `new SomeConcreteClass()` calls inside logic that should not care about the concrete type, and every new type means editing that logic;</span></Verdict>
  <Verdict ok><span>you are writing a framework or base class, and its users should be able to plug in their own types by subclassing, without changing your code.</span></Verdict>

### The `new` call it removes

A `new` call ties the code that contains it to one concrete class. That is fine at the edges of a program, where objects are put together. Inside an operation that should work with any kind, such as spawning a wave, it is a smell: the operation can only ever make the one class it names. Factory Method moves that one line into an overridable method, so the operation keeps working while the type changes.

<Grid cols="1fr 90px 1fr" narrowCols="1fr">
  <AnnotatedCode
    wide={false}
    caption="Before: the loop can only make wolves"

SpawnWave(size) {
  ...
  var e = new Wolf();
  ...
}
`}

`}

### Parameterised factory method

A factory method can take a parameter that says which kind of object to make. The base class gives defaults, and a subclass overrides the method to add or replace some kinds, calling the base version for the rest:

<AnnotatedCode
  caption="One factory method, several kinds: CaveLevel adds a boss"
  code={`
public abstract class Level
{
    protected virtual IEnemy CreateEnemy(string kind) => kind switch
    {
        "minion" => new Wolf(),
        _ => throw new ArgumentException($"Unknown enemy: {kind}"),
    };
}

public class CaveLevel : Level
{
    protected override IEnemy CreateEnemy(string kind) =>
        kind == "boss" ? new GiantBat()
                       : base.CreateEnemy(kind);
}
`}
  marks={[
    { line: 5, tone: 'ok', badge: '1', note: 'defaults live in the base' },
    { line: 6, tone: 'warn', badge: '!', note: 'unknown kind = runtime error' },
    { line: 12, tone: 'concrete' },
    { line: 13, tone: 'concrete', badge: '2', note: 'add one kind' },
    { line: 14, tone: 'concrete', badge: '3', note: 'the rest from the base' },
  ]}
/>

This keeps the hierarchy small when one creator needs several kinds of object. The cost is back in the strings: an unknown kind is a runtime error, not a compile error, so prefer an `enum` for the parameter.

### Simple Factory is not this pattern

A common relative is the "simple factory": a static method with a `switch`, such as `EnemyFactory.Create("cave")`. It is useful, because it puts every `new` in one place, but it is not a GoF pattern and works differently. There is no subclass and no override; one class knows every concrete type, and adding one means editing that `switch`. Factory Method spreads the decision over subclasses instead, so a new kind is a new class, and nothing that exists changes.

### When a constructor or DI is enough

If the caller already knows which object it needs, it can create it and pass it in. Giving <Role kind="primary">Level</Role> an <Role kind="contract">IEnemy</Role> in its constructor, or registering one in a dependency injection container, solves the same problem without a subclass per type. That is usually the better choice in application code. Factory Method fits when the base class needs fresh objects <Key>while it runs</Key>, more than one, or at a moment it decides, and when subclassing is already how the class is meant to be extended.

### Pitfalls

<Pitfall title="A subclass just to choose a type">

If <Role kind="concrete">ForestLevel</Role> exists only to override <Role kind="contract">CreateEnemy</Role>, you have a class per enemy type. When the levels differ in nothing else, passing a `Func<IEnemy>` or an object in the constructor is lighter.

<CodePair
  bad={"class ForestLevel : Level {\n  override CreateEnemy() => new Wolf();\n}"}
  good="new Level(() => new Wolf())"
  badLabel="heavy"
  goodLabel="lighter"
/>

</Pitfall>

<Pitfall title="Calling the factory method from the constructor">

In C#, a base constructor that calls a virtual method runs the subclass's override before the subclass's constructor body has run, so anything its own constructor body sets is not set yet. Call the factory method from ordinary methods, as `SpawnWave` does.

<CodePair
  bad="Level() { _e = CreateEnemy(); }"
  good="SpawnWave() { var e = CreateEnemy(); }"
  badLabel="runs too early"
  goodLabel="runs when needed"
/>

</Pitfall>

<Pitfall title="Making the factory method public">

It then becomes a second way for outside code to create objects, and callers start relying on it. Keep it `protected` unless creating objects is meant to be part of the class's public job.

<CodePair
  bad="public IEnemy CreateEnemy()"
  good="protected IEnemy CreateEnemy()"
  badLabel="leaks"
  goodLabel="a hook"
/>

</Pitfall>
