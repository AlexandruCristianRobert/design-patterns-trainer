# Quiz M2 — The 400-question bank — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Grow the Quiz bank from 20 to 400 reviewer-approved questions across the ten Quiz Topics. Before that, harden the content validator and finish the feature polish deferred from M1.

**Architecture:** Content lives in `content/quiz/<topic>.en.yaml` and is validated by vitest (`web/src/content/quizRules.ts` + `quiz.test.ts`). Output questions are compiled and run by `QuizOutputTests` (.NET). The content tasks are run by the controller as a loop:
1. an **author** subagent appends the batch;
2. a fresh **reviewer** subagent returns OK / NOT OK per id;
3. the author rewrites every NOT OK question;
4. the reviewer re-checks only those, until every question is OK;
5. the validator and the compiler tests run, then the controller commits.

The author and the reviewer are separate agents, because subagents cannot start subagents.

**Tech Stack:**
- the web app: React 19 + TS + vite, vitest, zod 4, `yaml`;
- the content tests: .NET 10 xUnit (`DesignPatterns.Content.Tests`, `CompilerService`, `LoadedProgram`).

**Spec:** `docs/superpowers/specs/2026-11-06-dotnet-quiz-design.md`, §2 M2, §3, §9. **Authoring reference:** `docs/superpowers/plans/2026-11-06-quiz-m2-authoring-guide.md`.

## Global Constraints

- One correct Option out of exactly four; the Options are shuffled, so **Explanations never mention a letter**; **all/none of the above is banned** (spec §3.2).
- Senior level; modern .NET (8/10, C# 12–14); no difficulty field (spec §3.1).
- Ids are kebab-case, unique across the bank, and stable: existing questions are never edited, reordered or re-id'd (spec §3.2).
- Topic targets (spec §3.1), each including the 2 existing questions:
  - csharp-language 50, clr-memory 40, async-concurrency 45, collections-linq 40, aspnet-core 50;
  - efcore-data 40, architecture-design 40, testing 30, web-distributed 35, security-performance 30.
  - Total: **400**.
- Length bias: across the bank, the correct Option is the strictly longest in **≤ 40%** of questions (spec §3.3). The authoring guide uses a ≤ 30% per-batch working limit, plus a ≤ 30% shortest limit.
- Every content question needs reviewer approval: "rewrite every not-OK question and resubmit until the reviewer approves all of them and the full count exists" (user rule). M2 ships only when every topic meets its target and every question is approved (spec §2).
- Keep the app name "Design Patterns Trainer" and every internal id.
- The unit tests are vitest. The e2e tests are Playwright on port 5299; the compiler e2e specs need `npm run build:dotnet` first.

// Prints "<topic>\t<id>\t<first line of question>" for every Quiz Question: the overlap index for authors and reviewers.
import { readFileSync } from 'node:fs'
import { fileURLToPath } from 'node:url'
import { parse } from 'yaml'

const dir = fileURLToPath(new URL('../../content/quiz/', import.meta.url))
const topics = parse(readFileSync(dir + 'topics.yaml', 'utf8'))
for (const t of topics) {
  let questions
  try { questions = parse(readFileSync(`${dir}${t.id}.en.yaml`, 'utf8')) ?? [] } catch (e) { if (e.code === 'ENOENT') continue; throw e }
  for (const q of questions) {
    const line = q.question.split('\n').map((s) => s.trim()).find((s) => s && s !== 'What does this program print?') ?? q.question.trim()
    const first = q.code ? `${line} [output: ${q.code.split('\n').find((s) => s.trim())?.trim()}]` : line
    console.log(`${t.id}\t${q.id}\t${first}`)
  }
}

## Content tasks (3–12)

Each content task is run by the **controller**, with the same procedure:

1. **Index.** Run `node web/scripts/quiz-index.mjs > <workspace>/index-before-<topic>.tsv`.
2. **Author.** Dispatch one author subagent (Opus) with:
   - the authoring guide path;
   - the topic, its batch size and its coverage list from the task;
   - the index file path;
   - the required number of output questions;
   - a report path.

   The author appends the batch to `content/quiz/<topic>.en.yaml`, runs the guide's self-check, and writes in its report the new ids plus its length-share counts. It does **not** commit, and it does not start subagents.
3. **Review.** Dispatch a fresh reviewer subagent (Opus) with:
   - the authoring guide path (the rubric);
   - the topic file path and the list of new ids to review;
   - the index file path;
   - a verdict path.

   It writes `<id>: OK` or `<id>: NOT OK — <reason>` for every new id, and may consult Microsoft Learn.
4. **Fix loop.** Send the NOT OK lines to the author (SendMessage resume). The author rewrites only those questions, keeping or changing ids per spec §3.2, and reruns the self-check. Then re-dispatch a reviewer on only those ids. Repeat until every id is OK. Rounds 4 and later use a fresh author.
5. **Verify and commit.** Run the guide's self-check and confirm the topic count with `node web/scripts/quiz-index.mjs | grep -c "^<topic>\t"`. Then commit `content(quiz): <topic> bank (<N> questions, all reviewer-approved)`.

The per-topic `QUIZ_TOPIC_MIN` floor of 2 stays until Task 13, so a half-finished bank never breaks the build.
