> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Strategy, Decorator, Factory Method and Singleton are fully built, the same way Observer is. Each has a Lesson (text, Structure Diagram, Interaction Scene, runnable example), graded Exercises and Exam Questions, so the Catalog shows 5 built Patterns and exams can mix them.

**Architecture:** Content-only, apart from Task 1's follow-ups. Each Pattern copies Observer's file layout and lesson components exactly. The existing loaders, .NET validator, Lesson, Exercise and Exam pages pick the files up with no code changes.

**Tech Stack:** M3 stack. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-22-design-patterns-trainer-design.md`, milestone M4. The relevant sections are §3 (Catalog and content, Tiers, Lookalikes, Lesson sections, Exercise Kinds, Exam Questions), §4 (Grading: Contract, Checks; "Singleton thread-safety is a structural Check") and §5 (C# runtime rules). Also read `CONTEXT.md` and the M3 plan's appendix of M3 follow-ups. M1–M3 are on `main`.

  - `uxkin:no-ui-slop` for UI work

- **Layout:** every Pattern copies `content/patterns/observer/` exactly. That means `pattern.yaml` (id, category, tier, version, lookalikes, exercises, examQuestions, roleNames), `text.en.yaml`, `lesson.en.mdx`, `example.cs`, `structure.yaml`, `scene.yaml`, `exercises/<id>/…` and `exam/<id>/…`.
- **Lesson sections:** fixed ids and order: `problem`, `analogy`, `structure`, `interaction`, `example`, `when-to-use`. Use the same MDX components as Observer.
- **Unique domains:** every Exercise, Exam Question and Lesson example in the whole app uses a domain no other one uses. The domains already taken are listed in the **Domain registry** below. Each task appends its domains to that registry in its report, and the controller carries the list forward.
- **No pattern giveaway:** an Exam Question's Contract and `en` title/scenario never name the Pattern or its roles. `roleNames` lists the role words, and the validator enforces them, including plurals.
- **Lookalikes:** only Catalog pattern ids. A comparison with something outside GoF goes in the lesson text, not in `lookalikes`. Examples are Simple Factory and a static class.
- **Exam Questions and Lookalikes:** at least one Exam Question per Pattern uses a scenario where a Lookalike is plausible but this Pattern is what's called for (spec §3).
- **Singleton thread-safety:** a structural Check accepts `Lazy<T>`, a static initializer, or a double-checked `lock` (spec §4).

### Test budget (user requirement: M4 test runtime ≤ 30 minutes in total)

1. Each task runs **only** the commands listed in its "Verify" step. There are no full `npm test`, `npm run e2e` or `dotnet test` runs inside tasks, except in Task 10.
2. **.NET content checks:** filter them to one Pattern with `dotnet test tests/DesignPatterns.Content.Tests --filter "DisplayName~<id>/"`. Add `--filter "DisplayName~<id>"` for the example test.
3. **Browser checks of a Lesson:** at most one Playwright screenshot script per Lesson task, at 390 and 1440 px. This is a visual check, not a test run.
4. **Reviewers run no tests.**
5. **The full suites run twice:** once at the end of Task 10, and once by the controller after the final fix wave. e2e is not run twice in a row unless it fails.
6. **Reporting:** every implementer reports the wall-clock seconds of each test command in its report. The controller keeps the running total in the ledger. If the total passes 25 minutes, later tasks drop to the single most relevant filtered command.

## Rulings made in this plan

1. **Two tasks per Pattern.** Each Pattern is split into a Lesson task and a Practice task (Exercises and Exam Questions). One task per Pattern would be too large for one review. The Practice task depends on the Lesson task's `pattern.yaml`.
2. **Exercise ids.** Standard Patterns use the Observer ids (`complete`, `refactor`, `build`). Tricky Patterns use descriptive kebab-case ids, listed in `pattern.yaml` in kind order: complete, refactor, refactor, build, build. Each id must be unique within its Pattern.
3. **Tier enforcement.** A content test (Task 1) enforces the Tier counts for Exercises, Exercise kinds and Exam Questions, so a Pattern can't ship short.
4. **Singleton Checks.** There are no real threads, so a Check can't race two calls. Singleton Checks test behaviour (same instance, lazy creation where the Exercise asks for it) plus the structural thread-safety Check.
5. **Pattern order.** Strategy, then Decorator, then Factory Method, then Singleton. That is easiest to hardest, so the content conventions settle before the Tricky Patterns.

## Review Focus

1. **Valid solutions rejected.** A reasonable, correct alternative design must pass. For Strategy that includes a delegate or lambda strategy where the Contract allows it. For Decorator, a decorator that forwards through an abstract base. For Singleton, any of the three thread-safe forms. Each Practice task's Checks must not hard-code one implementation. Its report names the alternatives it deliberately accepts.
2. **Hidden requirements.** Every behaviour a Check enforces is stated in the scenario. Tests: reviewers check this in every Practice task.
3. **Giveaways across Patterns.** Now that 5 Patterns exist, Identification is real. A scenario that names a role word of another Pattern (for example "strategy" in a Decorator question) is misleading. Tests: the validator's role-name rule applies to the question's own Pattern only. Reviewers also check scenarios against all built Patterns' `roleNames`.
4. **Tier counts.** A Tricky Pattern must not ship with 3 Exercises. Tests: the Task 1 content test.
5. **Lesson at 390 px.** Lessons must be fully usable at 390 px. The M2 follow-up said the Structure Diagram is cropped there. Tests: one screenshot per Lesson task, plus the Task 10 smoke e2e asserts no horizontal overflow.
